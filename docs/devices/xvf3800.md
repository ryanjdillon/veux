# XVF3800 host control

This doc records the facts that the `xvf3800` driver depends on. Each fact
has a source. "Unconfirmed" means that a test on hardware is necessary.

## Requirements

This table is for the USB link. For the ESPHome link, see
[esphome.md](esphome.md).

| Need | Detail |
|------|--------|
| Firmware | The stock Seeed USB firmware, USB VID `2886`, PID `001a`. The I2S firmware does not enumerate on USB, so veux reaches it over ESPHome only. |
| Access without root | A udev rule. See [Setup](#setup). |
| DFU image | You supply a USB DFU image file. veux bundles none. |

## USB identity

- VID `0x2886`, PID `0x001A` (SEEED-PY). DFU uses the same IDs.
- Control goes to endpoint 0 with the device recipient. No interface claim
  is necessary (XMOS-DC). This works while `snd-usb-audio` is bound.
- Only the USB firmware enumerates on USB. The I2S firmware, used under a
  XIAO ESP32S3, does not.

## Setup

veux opens the device without root. This needs a udev rule. On NixOS:

```nix
services.udev.extraRules = ''
  SUBSYSTEM=="usb", ENV{DEVTYPE}=="usb_device", ATTR{idVendor}=="2886", ATTR{idProduct}=="001a", MODE="0660", GROUP="wheel"
'';
```

- Use a group, not `TAG+="uaccess"`. The helper runs over SSH, so the user
  has no seat. Also, NixOS puts `extraRules` in `99-local.rules`, after the
  rule that applies `uaccess`, so the tag has no effect.
- The rule matches the `usb_device` node, which libusb and dfu-util open.
- The USB firmware, Safe Mode, and DFU mode all use `2886:001a`.

On other distributions, put the same line in
`/etc/udev/rules.d/60-xvf3800.rules`. Then run
`udevadm control --reload && udevadm trigger`, and connect the device again.

## Control transfers

| Field          | Write                     | Read                          |
|----------------|---------------------------|-------------------------------|
| bmRequestType  | `0x40`                    | `0xC0`                        |
| bRequest       | `0`                       | `0`                           |
| wValue         | command ID                | command ID `\| 0x80`          |
| wIndex         | resource ID               | resource ID                   |
| wLength        | payload bytes             | payload bytes + 1             |
| Data           | payload                   | status byte, then payload     |

- Resource IDs and command IDs are 8 bits. Command IDs are 0 to 127.
- Status 0 is success. Status 1 and 64 mean "retry". Retry after 10 ms, up
  to 100 times (SEEED-PY, ESPHOME). Other values are errors.
- The maximum transfer is 64 bytes (XMOS-DC). Unconfirmed if the status byte
  is part of the 64 bytes.
- Values are little-endian (SEEED-PY), confirmed on hardware.

## Data types

| Type    | Bytes | Encoding                     |
|---------|-------|------------------------------|
| uint8   | 1     | raw                          |
| char    | 1     | ASCII, trailing NUL removed  |
| uint16  | 2     | little-endian                |
| int32   | 4     | little-endian                |
| uint32  | 4     | little-endian                |
| float   | 4     | IEEE-754 binary32, LE        |
| radians | 4     | same as float                |

The "count" of a command is the number of values, not bytes.

## Firmware versions

Command availability changes with the firmware. The driver reads `VERSION`
(resource 48, command 0) first. Then it hides the commands that need a later
version. SEEED-FWLOG lists the version of each feature.

## Persistence

- `SAVE_CONFIGURATION` (48/9) saves all writable parameters to flash.
- `CLEAR_CONFIGURATION` (48/10) reverts to defaults. Then reboot.
- No command reads the saved values. Reads give runtime values only.
  Thus veux records a snapshot of the runtime values at each commit, and
  uses the snapshot as the persisted state. The snapshot is on the host
  that has the USB connection, in
  `$XDG_STATE_HOME/veux/xvf3800-<serial>.toml` (default
  `~/.local/state/veux`). It keeps only the writable values.
- The snapshot is not valid after a firmware change. veux deletes it
  before a flash, and ignores a snapshot from other firmware. veux does not
  send `CLEAR_CONFIGURATION`, so it cannot see a clear by another tool.
- A device without a USB serial number gets no snapshot.
- Unconfirmed: the exact set of saved parameters, and whether `REBOOT` loads
  the saved values or the defaults.

## Firmware update

- USB DFU class on 2886:001A. Alt setting 0 is factory (read-only). Alt
  setting 1 is the upgrade slot. SEEED-DFU gives a transfer size of 256
  bytes; the board reports 4096 (see the test results).
- A bad image falls back to the factory image after reboot.
- Images are in the Seeed repository, under `xmos_firmwares/usb/`.

## Firmware types and switching

- The USB firmware updates only over USB DFU, and the I2S firmware only over
  I2C DFU. The factory image (Safe Mode) accepts both.
- Safe Mode: power off, hold Mute, and power on. The red LED blinks. It
  enumerates as `2886:001a`: alt 0 is factory, alt 1 is upgrade.
- I2S to USB goes through Safe Mode:
  `dfu-util -d 2886:001a -R -e -a 1 -D <usb image>`.
- USB to I2S needs no Safe Mode, because USB firmware 2.1.1 offers DFU while
  it runs.
- The ESPHome satellite expects the formatBCE image
  `application_xvf3800_inthost-lr48-sqr-i2c-v1.0.7-release.bin` (I2S master,
  48 kHz). Seeed's own I2S 1.0.7 image is a different file that reports the
  same version. Do not use it.
- The formatBCE ESPHome component flashes the XVF3800 over I2C at every ESP
  boot when the version is not its own. Turn that off (`firmware: !remove`)
  before a Safe Mode session, so the ESP cannot race a USB DFU.
- Sources: Seeed wiki (Safe Mode), Seeed repo issues #8 and #12, formatBCE
  issue #52, and `respeaker_xvf3800.cpp` at formatBCE 542a05d.

### `veux firmware`

`veux firmware <device> <image>` writes an image to the upgrade slot (the
DFU alternate setting named "Upgrade"), with the steps of
`dfu-util -R -e -a 1 -D`. It shows the running version, the slots, and the
image size and sha256, and asks before it writes. A device on a remote host
is flashed by the helper on that host.

- If the device runs its application (DFU protocol 1), veux sends DFU_DETACH
  and waits up to 10 s for the device to come back in DFU mode.
- Blocks use the transfer size of the DFU functional descriptor (4096 bytes
  on this board).
- After the download veux sends DFU_DETACH, then a USB reset. The detach
  makes the board boot the new image.
- veux does not read a version from the image. Check the sha256 against the
  release.
- The first flash from I2S firmware needs Safe Mode, because the I2S
  firmware is not on USB.

## ESPHome

The ESPHome component talks to the XVF3800 over I2C (address `0x2C`) from
the ESP32. It exposes mute, the firmware version, the beam direction, the
mute button, and some LED and beam methods. It does DFU over I2C through
resource `0xF0`. Most PP and AEC parameters are not exposed as entities.

The ESPHome satellite firmware needs the API actions `xvf_get`, `xvf_set`,
and `xvf_flash`. See [xvf-actions.yaml](../../examples/esphome/xvf-actions.yaml).
With the first two, veux runs this driver over ESPHome: `EsphomeDevice` is
a `ControlPort`, and each call is one I2C transfer. See the raw
parameter actions in `docs/devices/esphome.md`.

## Hardware test results

Tested on 2026-11-13: USB firmware 2.1.1 on a Linux host, through
the helper, with `snd-usb-audio` bound.

- Byte order is little-endian: `aec.mic_array_geo` reads ±0.0333 m on a
  square of 4 microphones (array type 2).
- Vendor control works while `snd-usb-audio` holds the audio interfaces
  (0 to 2). Control is interface 3, DFU is interface 4, HID is interface 5.
- The generic 2.1.1 image reports `app.bld_msg` = `ua-io16-sqr` (16 kHz,
  2 channels).
- `audio_mgr.selected_azimuths` is NaN without speech, as documented.
- All 80 parameters of the command table read, and runtime writes read back.
- Two LED writes, the first after the board booted the new firmware, got
  status 8 (`CONTROL_ERROR`) on the read-back. Later writes did not.
- The DFU transfer size is 4096 bytes, not 256. veux reads it from the DFU
  functional descriptor.
- The USB firmware reports DFU protocol 2 (DFU mode) on its DFU interface
  while it runs. The protocol code does not tell the modes apart; the
  control interface does.
- A USB reset after a download does not reboot the board. DFU_DETACH after
  the manifest does. veux sends it.
- Safe Mode reports `ver=0003`, with alt 0 Factory, alt 1 Upgrade, and alt 2
  DataPartition. The upgrade slot reads back 933120 bytes.
